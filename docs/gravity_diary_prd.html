01 产品愿景

一本真正属于你的日记

大多数笔记工具把你变成数据的管理者——分类、标签、链接、数据库。Gravity Diary 的出发点恰恰相反：写，就是写。没有层级，没有仪式感，没有打开就要先想"这条记录该放哪"的焦虑。

但自由书写产生的大量非结构化内容，长期来看极难自我回顾。Gravity Diary 的第二层野心是：让 LLM 做那个耐心的读者，代替你从数年的流水中提炼出真正有价值的洞察。

核心主张

写作是输入，洞察是输出。前者要求自由，后者要求智识。两者本质上是矛盾的——我们用"写作界面极简、分析层异步"的架构化解这一矛盾。

设计原则

  • P1 写作时零干扰。AI 的存在对用户不可见，分析永远在后台、在用户主动触发后运行。
  • P2 数据完全属于用户。日记内容和分析结果均存储为本地 JSON 文件，不强制依赖任何云服务。
  • P3 渐进增强。不使用 LLM 功能时，应用与普通 Markdown 日记无异，没有任何功能降级。
  • P4 诚实的不确定性。LLM 的输出明确标注为"建议参考"而非"客观事实"，避免人工智能权威错觉。

02 核心功能

写作层

写作层是用户每天接触的界面，设计目标是让思维和手指之间的摩擦降至最低。

重力时间线

最新内容始终置顶，历史记录向下沉落。时间是重力，不是分隔符。无需翻页，当天内容就在视口顶端等你。

无边界白板

无分页、无字数上限、无章节。内容连续延伸，不受任何格式容器约束。一块完整的画布。

内嵌编辑 + 浮动工具栏

直接在页面上书写，工具栏随选中文本出现，不选中时自动隐藏。支持 Markdown 快捷语法。

双栏布局

左侧是全屏写作区，右侧日历视图支持日、周、月、年粒度切换，点击任意日期定位对应记录。

支持的内容类型

以下内容格式均通过 Markdown 语法触发，无需额外操作：文本段落、有序与无序列表、引用块、表格、图片嵌入、LaTeX 数学公式、待办事项（含完成状态追踪）。

03 LLM 智能层

把日记变成镜子

智能层是一个异步分析管道，完全独立于写作界面。用户可以随时触发分析，也可以设置定期自动运行（如每周一次）。分析结果汇总在右侧边栏的独立「洞察」视图中，与日历视图并列。

分析分为三个独立模块，每个模块对应一类洞察需求，可单独启用或禁用。

技术说明

LLM 调用默认使用用户自己配置的 API Key（OpenAI / Claude / 本地 Ollama 均支持）。内容在发送前经过本地分段，每次调用不超过 8,000 字，避免暴露完整日记上下文。

04 主题分析

你把时间花在哪里

主题分析模块从日记内容中归纳出反复出现的议题，并量化每个主题的出现频率与时间跨度，帮助用户看清自己真实的注意力分配。

主题提取 + 时间占比
按月或季度聚合，支持自定义时间范围
模块 A

LLM 对每一条日记条目进行语义分类，归入若干主题桶（桶由首次分析时自动生成，后续可手动调整）。分析完成后，系统计算每个主题在指定时间窗口内的出现次数、覆盖天数，以及在总体内容中的权重占比。

主题时间线视图

每个主题可展开查看其活跃时间分布——哪些周特别密集、哪些月几乎销声匿迹。用于回答"我上个季度到底在忙什么"这类问题。

典型洞察

「你在过去六个月里有 71% 的日记涉及工作项目，但关于身体状态的记录仅在三月和四月出现过共 8 次。」这类发现往往让用户意识到自己从未意识到的注意力偏斜。

05 困难识别

长期遇到的阻力在哪里

这是三个模块中最需要细心设计的部分。目标不是简单的情绪分析（正/负面），而是从流水般的叙述中识别出有结构的困难——反复出现的卡点、长期未解的矛盾、被反复提及的压力源。

反复出现的困难模式
跨时间维度聚类，区分偶发事件与系统性阻力
模块 B

LLM 被要求以"困难的观察者"身份阅读日记：识别描述挫败、卡顿、压力、冲突或自我怀疑的段落，提取其背后的结构性原因（而非表层情绪），并跨时间段比对是否反复出现同类问题。

示例输出 · 识别到的困难模式

困难报告 · 最近 6 个月
高频 深度工作被频繁打断。共出现 14 次，集中在周三至周五。描述包括「又没进入状态」「开了三小时会什么都没做」。
中频 对自身进展评价偏低。出现 9 次，通常在月末集中爆发，伴随与他人比较的叙述。
低频 技术选型焦虑。出现 4 次，每次均在新项目启动前后，持续时间约 1-2 周。

分析的边界

困难识别模块有意避免以下行为：情绪诊断（不输出"你有焦虑倾向"此类标签）、因果归因（不判断"这是因为……"）、价值判断（不评价困难"是否合理"）。输出只呈现观察到的模式，解读留给用户自己。

06 建议系统

有上下文的建议，不是通用鸡汤

建议是最后一层，只在用户主动请求时生成，不自动推送。其质量取决于主题分析和困难识别的积累深度——使用时间越长，建议越有针对性。

情境化建议生成
基于历史分析结果，聚焦可操作的具体行动
模块 C

建议生成时，系统将主题分析结果和困难报告一并送入 LLM 上下文，要求其生成分层建议：立即可执行（本周内）、中期调整（1-3 个月）、结构性反思（长期习惯与策略）。

建议示例 · 基于过去 6 个月数据
立即 你的深度工作集中在周一至周二，建议将周三上午也划入保护时段，在日历中设为不可约区。
中期 月末自我评价偏低的模式已持续 4 个月。建议尝试在每月最后一周提前做「已完成清单」而非「未完成清单」，从记录开始重构评价视角。
长期 身体相关记录明显稀少，且与工作强度呈负相关。这可能是一个值得单独关注的系统性取舍，而非时间问题。

设计约束

建议模块的提示词中明确要求 LLM：不使用「你应该」「你必须」等指令性语气，每条建议说明其背后的观察依据，不生成心理健康领域的专业建议，对不确定的推断显式标注置信度。

07 数据模型

JSON 文件结构

所有数据存储在单个 JSON 文件中，包含日记内容和 LLM 分析结果两个顶层字段。文件可直接放入 Google Drive 或 OneDrive 目录实现跨设备同步。

08 隐私设计

数据主权在用户手里

日记是极度私密的内容。隐私设计不是一个附加功能，而是整个系统架构的前提。

  • —不存在任何服务端。应用是纯 HTML 文件，不依赖任何后端。所有数据仅在用户本地浏览器与用户自选的存储位置之间流动。
  • —LLM 调用由用户控制。用户配置自己的 API Key，系统显示每次调用将发送的内容摘要，用户确认后才发起请求。支持本地模型（Ollama）以实现完全离线分析。
  • —分段发送，不暴露全文。每次 API 调用仅包含一个时间窗口的内容片段（约 2,000-8,000 字），系统不会将完整日记一次性发送到任何外部服务。
  • —云同步是可选的，且基于通用协议。JSON 文件放到任何支持文件同步的服务（Google Drive、OneDrive、Dropbox、本地 NAS）即可跨设备使用。应用本身不与这些服务有任何集成依赖。
  • —分析结果可单独清除。用户可以随时清除 intelligence 字段的全部内容，不影响日记正文，也不触发任何外部通知。
