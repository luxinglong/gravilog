Gravilog 存储机制一页读懂

这套机制可以用一句话记住：编辑器先把最新内容落到浏览器本地，再用一个“容量为 1 的写入桶”串行写入链接的 JSON 文件；挂载时用上次同步指纹判断该用本地、云端，还是停下来让人合并。

核心心智模型

本地缓存是快速草稿区，链接文件是可同步的正本。`pending sync` 表示“本地可能比云端新”。`last synced fingerprint` 表示“上一次确认两边一致的内容”。

四个存储角色

编辑器 DOM`doc.innerHTML` 是当前屏幕内容源，日历、统计、todo 一起组成 snapshot。
localStorage保存正文、日期、统计、todo、meta，以及 `diary_pending_sync` 和同步指纹。
IndexedDB只负责记住 File System Access API 的文件句柄，让下次启动能尝试恢复链接。
链接 JSON 文件通过文件句柄读写，导出为 v2 格式，是云盘同步软件实际同步的单文件。

Token-bucket 写入流

这个桶的关键不是限速，而是合并抖动：用户连续输入时，文件层只需要追上最后一个 snapshot，中间状态不用逐个写入。

本地优先

每次编辑先生成 snapshot

  • `save()` 是强保存：本地落盘后立刻排队写文件。
  • `scheduleLocalDraftSave()` 是输入时的延迟本地保存，减少每个键击的工作量。
  • `pending=true` 会把状态改成“本地有未同步内容”。
  • `latestFileSnapshot` 总是指向最后一次要写到文件的版本。

function queueFileWrite(snapshot){
  if(snapshot)latestFileSnapshot=snapshot;
  if(!syncReady)return;
  if(!fileHandle||!fileWritable){
    setPendingSync(true);
    return;
  }
  setPendingSync(true);
  if(fileWritePending){
    updateStorStatus(fileWritable);
    return;
  }
  fileWritePending=true;
  fileWritePromise=fileWritePromise
    .then(drainFileWrites)
    .finally(()=>{
      fileWritePending=false;
      updateStorStatus(fileWritable);
      if(latestFileSnapshot&&syncReady&&fileHandle&&fileWritable)
        queueFileWrite();
    });
}

async function drainFileWrites(){
  while(latestFileSnapshot&&fileHandle&&fileWritable){
    const snapshot=latestFileSnapshot;
    latestFileSnapshot=null;
    const ok=await writeToHandle(snapshot);
    if(!ok){
      latestFileSnapshot=snapshot;
      scheduleFileRetry();
      break;
    }
  }
}

async function writeToHandle(snapshot){
  const ok=fileWritable||await verifyHandle(false);
  if(!ok)return false;
  const target=snapshot||getLocalSnapshot();
  await writeSnapshotToHandle(fileHandle,target);
  rememberSyncedSnapshot(target);
  setPendingSync(false);
  return true;
}
写入桶

同一时间只有一个文件写任务

  • `fileWritePending` 就是令牌。令牌被占用时，新保存只替换桶里的 `latestFileSnapshot`。
  • `drainFileWrites()` 每次取走当前快照并清空桶；如果写入期间又来了新快照，循环会继续写最新的。
  • 写成功后才调用 `rememberSyncedSnapshot()` 和 `setPendingSync(false)`。
  • 写失败会把快照塞回桶里，2 秒后重试。
src/storage/conflict.js:23
function decideMountSnapshot(local,remote){
  const lt=snapshotTime(local),rt=snapshotTime(remote);
  const localHas=snapshotHasContent(local);
  const remoteHas=snapshotHasContent(remote);
  const pending=hasPendingSync()&&localHas;
  const lastSynced=getLastSyncedSnapshot();

  if(!localHas)return {action:'remote'};
  if(!remoteHas)return {action:'local'};
  if(!snapshotsDiffer(local,remote))return {action:'remote'};

  if(lastSynced){
    const localChanged=snapshotChangedSinceBaseline(local,lastSynced);
    const remoteChanged=snapshotChangedSinceBaseline(remote,lastSynced);
    if(localChanged&&remoteChanged)return {action:'conflict'};
    if(localChanged&&!remoteChanged)return {action:'local'};
    if(!localChanged&&remoteChanged)return {action:'remote'};
  }

  if(pending)return {action:'conflict'};
  if(!lt||!rt||lt===rt)return {action:'conflict'};
  if(lt&&rt&<>rt)return {action:'local'};
  if(lt&&!rt)return {action:'local'};
  return {action:'remote'};
}
挂载判定

冲突处理不是看谁更新这么简单

  • 最可靠的判断来自 `lastSynced`：分别问“本地是否偏离上次同步点”“远端是否偏离上次同步点”。
  • 两边都变了，进入 conflict，禁止自动覆盖。
  • 只有一边变了，就用变了的那一边。
  • 没有同步基线时，如果本地有 pending 且两边不同，保守进入 conflict。

function trySaveLocalSnapshot(snapshot){
  try{
    return saveLocalSnapshot(snapshot);
  }catch(firstError){
    try{
      clearLocalSnapshot();
      return saveLocalSnapshot(snapshot);
    }catch(secondError){
      clearLocalSnapshot();
      console.warn(
        'Local snapshot cache write failed; using linked file as source of truth',
        secondError
      );
      return rememberLocalSnapshotCache(snapshot);
    }
  }
}

function rememberSyncedSnapshot(snapshot){
  const normalized=normalizeSnapshot(snapshot);
  localStorage.setItem(LAST_SYNC_KEY,JSON.stringify({
    schemaVersion:SNAPSHOT_VERSION_V1,
    fingerprint:snapshotSyncFingerprint(normalized),
    savedAt:normalized.savedAt||new Date().toISOString()
  }));
  return normalized;
}

function snapshotSyncFingerprint(snapshot){
  const text=snapshotSyncPayload(snapshot);
  let hash=5381;
  for(let i=0;i<text.length;i++)
    hash=((hash<<5)+hash)^text.charCodeAt(i);
  return text.length+':'+(hash>>>0).toString(36);
}
缓存与基线

本地缓存失败时也尽量不断流

  • `trySaveLocalSnapshot()` 先写 localStorage，失败后清空旧缓存再试。
  • 如果浏览器存储还是满了，就把 snapshot 放进内存缓存，并把链接文件当作主要真实来源。
  • 同步基线只存轻量 fingerprint，不存完整正文，降低 localStorage 占用。
  • fingerprint 不包含 `savedAt`，所以只判断内容是否变了。

挂载时怎么选版本

启动或点击“链接文件”后，`syncFromLinkedFile()` 读取远端 JSON，再拿本地 snapshot 交给 `decideMountSnapshot()`。结果只有四种。

`remote`
本地为空、远端有内容，或者只有远端偏离上次同步点。读取云端并更新本地缓存。
`local`
远端为空，或者只有本地偏离上次同步点。使用本地，并写回链接文件。
`conflict`
两边都偏离上次同步点，或没有可靠基线但本地有 pending。暂停编辑，显示合并 UI。
`same` 的等价路径
代码里相同内容返回 `remote`，效果是两边一致时按远端刷新本地并清掉 pending。

链接、导入、导出分别是什么

链接文件使用 File System Access API 选择一个 `.json`，把文件句柄放进 IndexedDB，把文件名放进 localStorage。浏览器下次启动会尝试恢复句柄；权限没恢复时会显示待授权。

云同步不是直接调用云服务 API。Gravilog 只是写本机链接的 JSON 文件，真正的跨设备同步由 iCloud、OneDrive、Dropbox 等同步目录完成。

导入/导出不需要长期文件句柄。导出下载一个 v2 JSON；导入读取用户选的 JSON，迁移成 snapshot，更新本地，然后尝试写入当前链接文件。

Gotchas

  • 浏览器支持是硬前提。 文件挂载依赖 `showOpenFilePicker`，主要面向 Chrome/Edge；不支持时只能导入导出。
  • “云端已同步”只代表 Gravilog 写入了本地链接文件。 云盘客户端是否已经上传到另一台设备，不在这段代码控制范围内。
  • pending sync 是保护标记，不是错误。 没有文件权限、没有链接文件、写入失败时都会保持 pending，避免误以为远端已经安全。
  • 冲突时会锁住编辑器。 这是故意的：在两端都改过时继续自动写入，很容易覆盖另一台设备的内容。
  • 合并 UI 主要合并正文，辅助数据自动取并集或最大值。 dates 取并集，stats 每天取较大字符数，todos 按 id 合并。
  • localStorage 满了不等于所有保存都失败。 代码会退到内存缓存，并继续尝试写链接文件；但刷新前最好确认右侧状态已经不是“待同步”。
  • `savedAt` 是兜底排序依据。 有同步 fingerprint 时优先看内容差异；没有基线时才更依赖时间戳，所以设备时间不准会增加冲突概率。
